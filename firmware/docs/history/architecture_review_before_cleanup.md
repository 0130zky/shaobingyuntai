# 架构评估与演进方案

初次评估日期：2026-10-30。下文保留改造前的静态评估与目标方案。

第一轮实施完成职责拆分和发射机构控制入口收拢；第二轮完成反馈缓存、只读状态发布和 CAN 分发解耦。
现状见 `modules/shooter/README.md`。
下文列出的跨任务写拨盘、USB 入口约束、故障位归属、BSP 业务依赖及遥测直接读内部状态等问题已处理；
完整目标架构仍需分阶段实施，不能将本文目录树当成当前已实现的结构。

## 1. 判断

当前项目是 STM32F407 + FreeRTOS 的整车代码，叠加了“三摩擦轮 + 可替换拨盘电机”的台架用途。主要问题是状态归属、任务边界和硬件边界没有对齐。仅重命名文件夹不能解决。

建议采用 **按业务模块组织、由单个控制任务持有发射机构状态、通过显式硬件接口接入设备** 的静态 C 架构。保留 CubeMX、FreeRTOS、现有控制参数和已验证的保护规则，不引入通用消息总线、动态插件或每个模块一个任务。

值得保留的基础：

- `dial_port` 已把 RM3508 / DM4310 的反馈、闭环和发送差异隔离，并支持编译期二选一。
- 三轮控制已有统一快照、同步补偿限幅和独立保护。
- 遥测已有 DMA 忙时丢采样、单发送者等约束。
- 已有拨盘边界、堵转、DM 控制、遥控解析及上位机分析回归用例。
- 后台采集独占串口、界面读取记录的方向合理。

## 2. 当前的关键问题

| 问题 | 源码依据 | 影响 |
| --- | --- | --- |
| 同一拨盘控制链分属多个任务 | `RC_task.c` 调用 `Booster_RequestShot`；`BoosterTask` 调用 `Dial_Port_Update`；`PID_Task` 执行闭环和发送 | 临界区能保护局部访问，但不能保证整个控制拍采用同一份输入或同一时刻状态 |
| BSP 依赖具体业务对象 | `bsp_can.c` 包含 booster/gimbal/master 头文件，直接写 `BOOSTER`、`GIMBAL`、`MasterLink` | 换板、换整车组合或做主机测试时，都要牵动底层分发代码 |
| `booster_task.c` 承担多种职责 | 包含 USB 命令解码、来源选择、轮速控制、拨盘状态机、保护、遥测打包及诊断 | 修改一种职责需要理解大量关联状态，接口无法表达清楚边界 |
| 时间模型不统一 | PID 从 DWT 取实际 dt；拨盘计时 `+= 3`；轮速斜坡按 rpm/拍；发散判断按拍计数；任务使用相对 `osDelay` | 改调度会隐式改变斜坡、超时和检测行为，测试固定 3ms 难以覆盖 |
| 故障归属混乱 | 控制代码写 `RC_Data.Error_code`，辅助任务也修改此字段 | 拨盘故障成为遥控数据的一部分，读改写分散，故障含义难扩展 |
| 控制来源规则散落 | `RC_MasterEnabled`、`Booster_GetWheelSetpoint`、`Booster_DialCtrl` 各做部分判定 | 很难直接证明“某个构建允许哪些入口、失联后会发生什么” |
| 台架用途与整车启动耦合 | 当前 `freertos.c` 创建八个任务；`SysInit` 必须等待 BMI088 自检成功；USB 在 INS 任务启动 | 发射机构台架也受云台、IMU 和旧整车链路的启动条件影响 |
| 测试依赖源码文本结构 | 多个测试按函数签名和文本边界截取 C 函数，临界区替换为空操作 | 行为回归有价值，但文件拆分容易破坏测试，也无法验证并发交接 |

还发现两处应在迁移前核对的行为差异：

1. README 保留过往的 `0.10°` 越界余量等说明；当前 `dial_config.h` / `Booster_DialCtrl` 使用偏离跨度超过 `10°` 并累计约 `20ms` 的故障判据。应先记录当前真实行为，再决定是否调整；架构迁移不能把旧说明当作现状。
2. `BOOSTER_RC_ONLY` 目前主要作用于 `RC_MasterEnabled` 的掉线返回值。USB 接收仍调用 `Booster_UsbCmdHandler`，该函数仍写命令状态并调用 `Dial_Port_SetZero`；拨盘失联分支又直接读取 USB `link_ok`。从源码看，“仅遥控、USB 不接收控制和零点”尚未在所有入口形成完整边界。这是静态分析发现，未验证板端触发情况。

## 3. 目标模块

建议先在现有工程根目录内演进，避免同时移动供应商源码和整个项目根目录。

```text
Core/ Drivers/ Middlewares/ USB_DEVICE/  # CubeMX / 供应商代码，保持生成边界
board/                                 # 板级资源绑定、HAL 适配、IRQ 入口
devices/                               # 电机/IMU设备协议、原始反馈与硬件适配
protocols/                             # SBUS、裁判、视觉、遥测的编解码
control/                               # PID、滤波、同步计算等无 HAL 算法
modules/
  shooter/
    shooter.c/.h                       # 本模块唯一编排入口
    shooter_command.c/.h               # 指令来源、有效期和事件处理
    friction_group.c/.h                 # 三轮参考、同步、闭环、局部保护
    dial_fsm.c/.h                      # 拨盘动作与恢复状态机
    dial_axis.h                        # 拨盘轴接口，逐步从 dial_port 演进
    shooter_status.h                   # 对外只读状态和故障原因
  gimbal/                              # 云台业务
  estimator/                           # 姿态估计
  chassis_link/                        # 下板通信业务
services/
  telemetry/                           # 状态快照编码和发送管理
  health/                              # 故障汇总和灯光显示
app/
  app_init.c                           # 初始化顺序、注册和资源装配
  app_tasks.c                          # RTOS 调度外壳
config/
  profiles/                            # 发射台架、整车、标定构建配置
  shooter_config.h                      # 机构参数与控制参数
host/                                  # 后续整理上位机，初期可保留 tools 名称
tests/
```

依赖规则：

- 算法层只接受数值、状态和时间，不包含 `main.h`、HAL 或 RTOS 头文件。
- 业务模块依赖自身数据类型与设备接口，不直接操作 UART/CAN 句柄，不包含其他模块的 `*_task.h`。
- BSP/板级代码通过装配时绑定的处理入口交付数据，不引用 `BOOSTER` 等业务全局变量。
- `app_init` 是组装点，允许同时知道业务模块和板级实现；不要求通过运行时注册框架解耦。
- 编译期选择 RM/DM 实现即可。未出现运行时切换需求前，不必建立通用虚函数表。

## 4. 一拍控制如何执行

发射机构由一个 `ShooterControlTask` 驱动，按以下顺序执行：

```text
读取一致的反馈与输入快照
  → 判定控制来源、使能和链路有效期
  → 处理本拍有效事件
  → 推进拨盘状态机
  → 三轮参考/同步/闭环 + 拨盘轴闭环
  → 执行最终输出约束
  → 合成并提交 CAN 帧
  → 发布只读状态和控制时序
```

`shooter` 持有自己的 `shooter_ctx_t`，只有这个任务可以修改命令应用状态、目标、积分、堵转计时和动作状态。取消对外暴露整个 `BOOSTER` 的做法。其他任务读取复制后的状态，输入端提交请求。

建议提供类似以下接口；这里只表达边界，并非要求一次性改签名：

```c
void Shooter_Init(shooter_ctx_t *ctx, const shooter_config_t *cfg);
void Shooter_Step(shooter_ctx_t *ctx,
                  const shooter_input_t *input,
                  const shooter_feedback_t *feedback,
                  uint32_t now_ms, float dt_s,
                  shooter_output_t *output,
                  shooter_status_t *status);
```

输入快照保留各设备各自的接收时间与有效标记。同一软件快照不表示 CAN 反馈物理同步。拨盘反馈转换放入本拍控制入口，避免依赖另一个 2ms 任务提前刷新共享 `s_fb`。

CAN ISR 可以保留有界的帧解码和连续位置展开，但只发布设备反馈，不能修改业务状态或控制器。展开依赖相邻反馈，不能简单把原始帧改成覆盖邮箱而丢掉中间过窗信息。反馈快照先采用短临界区复制；后续若改双缓冲，必须明确缓冲区归属和读写协议。

## 5. 连续命令与离散事件分开

连续量（轮速、使能、模式）采用最新有效快照；离散请求（进格、退格、相位设置）具有来源、序号、时间和会话信息。

- 开火事件不能因为新增 RTOS 队列而变成动作积压。按明确的输入交接规则，在当前使能会话、本拍时效及当前动作状态下接受或拒绝，消费后不重试。
- 忙碌期间拒绝正向追加请求；失联/失能清除待处理动作，并作废旧会话。重连后保留“先松开再触发”的约束。
- 退弹、停机和正向请求的优先级显式定义；停机不依赖普通事件队列排空。
- 相位设置仅在失能时处理并返回确认；USB 台架命令应受构建配置与来源仲裁共同约束。
- 第一阶段不机械地把所有现有函数调用替换成 FIFO；先为现有接受/丢弃语义建立回归，再决定邮箱或有界队列。

接收端只负责帧合法性，`command` 模块统一决定该来源是否允许控制。`RC_LinkFresh()` 一类判定不应被多个控制器重复调用。

## 6. 拨盘状态显式化

目前多个布尔字段承载隐含状态，建议逐步改为：

```text
DISABLED → ALIGNING → HOLDING ↔ MOVING
                         MOVING → ROLLBACK → LOCKED
                         任意状态 → DISABLED（失能/反馈故障）
                         越界故障 → LOCKED（不自动回拨）
```

手动退弹与重新使能的恢复条件写成明确转移。状态机保留命令锁定起点/终点、固定网格、动作不堆积、有限回拨和故障锁定等规则；精确阈值以迁移前确认的当前实现为基线。

拆开三个概念：运动完成条件、闭环保持条件、故障判据。三轮 ready 当前仅供遥测，不能在迁移时顺手变成发弹门控。

`dial_axis` 初期继续使用现有 `dial_port_dm/rm` 的闭环实现。设备量程、传动比、符号属于设备适配；拨盘单格角度、回拨策略和连发停留属于机构业务。不要把设备替换与控制算法重写放在同一阶段。

## 7. 调度、时间、发送与故障

- 第一阶段保留当前相对延时和控制增益，先收拢状态归属。名义 3ms 不等于实际稳定 333Hz。
- 第二阶段统一显式 `now_ms` / `dt_s`：超时使用时间差，斜坡使用 rpm/s，堵转和发散持续时间使用真实经过时间；对异常 dt 定义停机/重置策略。
- 固定周期调度是后续选项：测量执行耗时、抢占和超期后，再独立切换绝对延时或定时通知。不能与搬文件同时改变时序。
- CAN `0x200` 的四槽仍由唯一发送入口合成；拨盘 DM 帧独立提交。控制任务有界提交，不能等待队列或总线空闲；防止旧非零命令在停机后继续排队发送。
- 发送失败反馈给模块的链路状态；“本机输出已经清零”不等于“执行器已经收到零输出”。
- 故障分别由模块拥有，汇总为只读位图与原因码；区分自动恢复和锁存恢复。健康服务负责显示，不能反向替代控制保护。
- 遥测读取控制拍完成时发布的状态，不临时调用会重新推导命令或更新控制状态的 getter。
- UART/USB 的 DMA 缓冲区由发送服务持有到完成。遥测允许丢帧；命令应答明确发送失败后的保留/重试规则。诊断计数的消费和发送成功语义也需明确。

台架 profile 只创建必要任务；整车 profile 再启用云台、姿态估计和下板链路。USB 初始化移到显式系统装配流程。没有 IMU 的台架构建不应无限等待 BMI088 自检，整车构建则保留其必要的启动约束。

## 8. 上位机与工程约束

上位机继续保留一个串口所有者。先拆 `telemetry_io.py` 中协议解码与 POSIX 串口实现，避免 Windows 上连离线解码也受 `fcntl/termios` 导入影响。再将时间重建、事件识别和逐发测量收拢为共享分析库，供 CLI、Tk 和 VS Code 使用。CSV 继续作为记录与回放格式；是否增加实时 IPC，应由延迟测量决定。

CMake 当前将大部分用户代码和头文件挂到一个可执行目标，不能强制依赖边界。逐步增加算法、协议、业务和板级目标，收紧头文件可见范围。主机测试直接链接纯 C 模块源文件，替代源码字符串抽取。保留原测试作为迁移基线，新增虚拟时钟、输入交接和完整状态转移测试。

`CMakeLists.txt` 已明确有一批依赖缺失 `chassis_task.h` 的旧源码不参与构建。先标记保留用途，待构建与引用确认后再清理；供应商目录里的重复副本也不应与业务迁移混在一次改动里。

## 9. 推荐实施顺序与验收

1. **建立真实行为基线**：核对 README 与实现、控制来源边界、当前构建 profile；保存现有用例与可复现输入输出。优先单独处理仅遥控配置的入口一致性。
2. **拆职责，保留调度**：从 booster 文件提取摩擦轮、拨盘状态机、指令解析和遥测；不同时改参数、故障阈值和发送格式。验收为同样输入产生同样目标、状态和输出。
3. **统一状态归属**：输入端提交请求；控制任务独占拨盘与摩擦轮状态，将反馈转换纳入本拍，移除跨任务直接修改。重点验证失联瞬间、忙碌请求、退弹打断和重连不补动作。
4. **统一时间模型**：用虚拟时钟覆盖变周期、长暂停和时钟回绕，再独立验证调度变更及实机响应。
5. **隔离产品组合和板级依赖**：增加台架/整车 profile，收紧 CMake 依赖；验证 RM、DM、标定构建，以及台架不接 IMU 的启动路径。
6. **整理上位机和历史代码**：共享分析库、串口平台适配、清理构建外源码，更新单一现状文档，将试验历史独立归档。

每阶段保留可独立验证和回退的改动。主机测试确认逻辑，固件构建确认集成，实际控制周期、总线异常和机械响应仍需对应的板上验证。
